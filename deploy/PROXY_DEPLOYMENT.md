# Прокси перед NexusData (`proxy_server.py`)

## Зачем

Раньше `python api_server.py` был единственным процессом: он же слушал
публичный порт, он же отдавал сайт/API, он же читал консоль Pterodactyl. Пока
его останавливали, чтобы безопасно заменить код при деплое (или если он падал
сам) — порт никто не слушал, и пользователи получали обрыв соединения вместо
страницы "технические работы".

Теперь `proxy_server.py` — это отдельный, предельно простой процесс, который
держит публичный порт **всегда**, независимо от того, жив ли реальный бэкенд
(`api_server.py`) за ним. Он не импортирует ничего из `main.py`/`config.py`
и не трогает БД — баг в остальном приложении не может уронить сам прокси.

## Что изменилось для деплоя

- Точка запуска теперь **`python proxy_server.py`** вместо `python api_server.py` —
  везде, включая локальную разработку.
- nginx на VDS **менять не нужно** — он по-прежнему смотрит на порт 8000
  (`deploy/onlyoffice/NATIVE_INSTALL.md`), просто теперь на этом порту сидит
  прокси, а не FastAPI напрямую.
- Реальный бэкенд (`api_server.py`) прокси запускает сам, как дочерний процесс,
  на внутреннем `127.0.0.1:8001` (не публикуется наружу).
- Консоль (Pterodactyl "Console" / stdin) теперь читает прокси, не бэкенд —
  команды те же, плюс новая `backend on|off|restart`.

## Новый порядок деплоя обновления

```
maintenance on Обновляем сервер, вернёмся через 5 минут
backend off
# ...заменить код (git pull / загрузить файлы)...
backend on
maintenance off
```

Всё время между `backend off` и `backend on` пользователи видят опрятную
страницу "Технические работы" вместо обрыва соединения — прокси продолжает
отвечать, даже когда `api_server.py` полностью остановлен.

Если бэкенд просто упадёт сам по себе (краш) — прокси обнаружит это
автоматически (недоступное соединение на 127.0.0.1:8001) и покажет ту же
страницу; поток-наблюдатель прокси сам поднимет процесс заново в течение
нескольких секунд, без ручного вмешательства.

## Переменные окружения (все опциональны, есть дефолты)

| Переменная | По умолчанию | Что это |
|---|---|---|
| `PROXY_HOST` | `0.0.0.0` | На чём слушает публичный прокси |
| `PROXY_PORT` | `8000` | Публичный порт (тот же, куда сейчас смотрит nginx) |
| `BACKEND_HOST` | `127.0.0.1` | Куда прокси стучится за реальным бэкендом |
| `BACKEND_PORT` | `8001` | Внутренний порт бэкенда |
| `PROXY_FORWARDED_ALLOW_IPS` | `127.0.0.1` | От кого доверять заголовку `X-Forwarded-For` на входе в `proxy_server.py` (см. раздел «Реальный IP клиента» ниже) |

## Реальный IP клиента (X-Forwarded-For)

Фактическая топология этого деплоя (по реальному конфигу nginx,
`nd.rp-asper.ru`): **интернет → nginx (публичный домен, TLS-терминация) →
`proxy_server.py` на `bapi.icedem.ru:8000` → `api_server.py` (127.0.0.1:8001,
уже внутри того же контейнера)**. Важная деталь — nginx проксирует на
`bapi.icedem.ru`, а не на `127.0.0.1`: значит nginx и `proxy_server.py`
живут на РАЗНЫХ хостах, и соединение между ними идёт по сети, а не по
loopback. TCP-пир, который видит `proxy_server.py`, — это публичный IP
самого nginx-сервера (в вашем случае — `92.38.222.172`), а не IP реального
посетителя сайта напрямую (тот уже свёрнут в `X-Forwarded-For` самим nginx).

nginx уже настроен правильно — `proxy_set_header X-Forwarded-For
$remote_addr;` (замена, не `$proxy_add_x_forwarded_for`) в `location /`
для `bapi.icedem.ru:8000`, это ценное значение, только что доехать ему
было некуда: `proxy_server.py` по умолчанию доверяет `X-Forwarded-For`
ТОЛЬКО от `127.0.0.1` (см. `PROXY_FORWARDED_ALLOW_IPS` в таблице выше), а
TCP-пир здесь — `92.38.222.172`, не loopback. Поэтому заголовок
игнорировался, и `proxy_server.py` (а через него и `api_server.py`) видел
клиентом IP самого nginx для КАЖДОГО запроса — отсюда `92.38.222.172` в
логах вместо настоящего IP посетителя/атакующего.

**Исправление** — на хосте, где реально запущен `proxy_server.py`
(`bapi.icedem.ru`, Pterodactyl-контейнер), выставить переменную окружения:

```
PROXY_FORWARDED_ALLOW_IPS=92.38.222.172
```

Ставится там же, где остальное окружение процесса (Pterodactyl → Startup
Variables егга, НЕ файл `.env` в репозитории — `proxy_server.py`
намеренно не читает `config.py`/`.env`, см. докстринг файла). После смены
нужен перезапуск именно `proxy_server.py` целиком (не просто `backend
restart` — та команда перезапускает только дочерний `api_server.py`, а
переменная читается самим прокси-процессом один раз при старте).

Если IP nginx когда-нибудь сменится (переезд на другой VDS) — не забыть
обновить и эту переменную; иначе форвардинг тихо перестанет доверять
источнику и снова начнёт показывать IP nginx вместо реального.

`proxy_server.py` дальше сам ПЕРЕПИСЫВАЕТ X-Forwarded-For на то значение,
которому доверяет (см. `_real_client_ip`/`_proxy()` в коде), прежде чем
передать его `api_server.py`, — заголовок от nginx никогда не долетает до
бэкенда как есть, только то, что решил сам `proxy_server.py`.

`SERVER_HOST`/`SERVER_PORT` из `.env` для самого бэкенда теперь не используются
напрямую в обычном режиме — прокси всегда переопределяет их в окружении
дочернего процесса на `BACKEND_HOST`/`BACKEND_PORT`. Они остаются рабочими,
только если запустить `python api_server.py` отдельно, в обход прокси
(для быстрой локальной проверки без консоли/техработ).

## Консольные команды (без изменений + одна новая)

```
status                       — текущее состояние подсистем
api on|off|restart           — вкл/выкл/перезапуск API (/api/*)
web on|off|restart           — вкл/выкл/перезапуск веб-морды (сайта/SPA)
workers on|off|restart       — вкл/выкл/перезапуск фоновых воркеров
backend on|off|restart       — вкл/выкл/перезапуск ВСЕГО backend-процесса — новое,
                                используйте перед заменой кода при деплое
maintenance on [текст]|off   — вкл/выкл режим технических работ
db check                     — принудительно проверить подключение к БД
```

`maintenance on/off` и `api`/`web`/`workers` продолжают работать ровно как
раньше, пока бэкенд жив (их читает `main.py`'s `maintenance_gate_middleware` +
SPA-баннер) — прокси в это не вмешивается и не дублирует эту логику. Прокси
показывает свою страницу техработ ТОЛЬКО когда бэкенд физически недоступен —
то есть именно тогда, когда штатный механизм ответить не может в принципе.

## Автоподъём остальных компонентов

Помимо самого бэкенда (который прокси уже поднимает заново — см. выше),
автоподъём есть ещё на двух уровнях:

- **`scheduler_process.py`** (только в multi-worker режиме,
  `UVICORN_WORKERS>1` и `DEBUG=false` — см. `api_server.py`): за этим
  дочерним процессом следит поток-наблюдатель внутри самого `api_server.py`
  (`SchedulerWatcher`, тот же паттерн, что и `_backend_watcher_loop` у
  прокси) — если процесс планировщика падает, он перезапускается
  автоматически в течение нескольких секунд, без вмешательства.
- **Здоровье БД**: `workers.py`'s `task_check_db_health` — лёгкий `SELECT 1`
  каждые 30 секунд, автоматически обновляющий `runtime_control.db_healthy` —
  ручная консольная `db check` по-прежнему работает, но больше не единственный
  способ узнать о проблеме с БД.

## Уровень выше прокси (Pterodactyl / systemd)

Сам `proxy_server.py` спроектирован падать крайне редко (минимум зависимостей,
никакого SQLAlchemy/main.py импорта), но strap-and-suspenders ради самого
верхнего уровня всё равно стоит настроить: убедитесь, что процесс-менеджер
(Pterodactyl egg / systemd unit / supervisor) сам перезапускает
`proxy_server.py`, если он всё же упадёт — например `Restart=on-failure`
для systemd, или соответствующий флаг перезапуска egg'а в Pterodactyl. Это
единственный уровень автоподъёма, который НЕ реализован в коде — по
определению некому перезапустить сам процесс, который всех перезапускает.
