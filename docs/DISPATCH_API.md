# API диспетчерской

Полное описание всего, что относится к диспетчеру: приём сообщений с игрового
сервера, отправка сообщений диспетчера, действия (челнок, груз, торпедный
удар), виртуальный склад, жизненный цикл раунда, исходящие вебхуки и внешний
клиентский API.

Реализация: [`routes/dispatch.py`](../routes/dispatch.py),
[`routes/warehouse.py`](../routes/warehouse.py),
опрос действий — [`routes/moderation.py`](../routes/moderation.py).

---

## 1. Как это устроено

Диспетчерская — не прямой канал управления игровым сервером. Сайт **никогда не
подключается к игровому серверу сам**; всё идёт через очередь задач:

```
        ┌──────────────┐   POST /server/dispatch          ┌──────────────┐
        │ Игровой      │ ───── сообщение игрока ────────► │              │
        │ сервер       │                                  │  NexusData   │
        │ (плагин)     │ ◄──── GET /server/actions ────── │              │
        │              │ ───── POST /actions/{id}/ack ──► │              │
        └──────────────┘                                  └──────┬───────┘
                                                                 │
                        ┌────────────────────────────────────────┼───────────┐
                        ▼                    ▼                   ▼           ▼
                  Админ-панель        Внешняя система      Discord-канал   Вебхук
                  (сессия+CSRF)      (client_api_key)       (эмбед)      (исходящий)
```

Всё, что «делает» диспетчер в игре, — это строка в таблице `server_actions`.
Игровой сервер сам её забирает и сам отчитывается о выполнении. Поэтому:

* Действие, поставленное при выключенном сервере, выполнится при его запуске —
  очередь не протухает сама по себе.
* Пока сервер не прислал ACK, задача считается невыполненной. Для сообщений
  диспетчера это используется явно: кнопка отправки блокируется, пока
  предыдущее сообщение не подтверждено (см. `/dispatch/pending`).
* Ответ `{"status": "ok", "action_id": N}` означает «задача поставлена», а не
  «выполнена в игре».

### Три уровня доступа

| Уровень | Как аутентифицируется | Кто это | Префикс |
|---|---|---|---|
| Игровой сервер | `X-API-Key: <API_KEY>` или `?api_key=` | плагин Barotrauma | `/api/v1/server/...` |
| Админ-панель | cookie `admin_token` + права страницы `dispatch` | сотрудники на сайте | `/api/v1/admin/dispatch/...` |
| Внешняя система | `X-API-Key: <CLIENT_API_KEY>` | сторонняя интеграция | `/api/v1/client/dispatch/...` |

`API_KEY` и `CLIENT_API_KEY` — **разные секреты** и это намеренно: тому, кто
только шлёт грузы, не нужен ключ, которым игровой сервер пишет всю телеметрию.
Если `CLIENT_API_KEY` пуст, клиентские эндпоинты закрыты полностью (401), а не
«пропускают всех».

### Права в админ-панели

Страница `dispatch` («Диспетчерская») разбита по операциям — они разные по
последствиям, и группе можно выдать только часть:

| Действие | Что открывает |
|---|---|
| `view` | эфир, статус раунда, остатки склада |
| `send_message` | отправку сообщений диспетчера в эфир |
| `shuttle` | отправку и отзыв снабженческого челнока |
| `cargo` | отправку груза (списывает склад) |
| `torpedo` | торпедный удар по координатам |
| `manage_warehouse` | правку склада |
| `manage_webhooks` | настройку адресов исходящих вебхуков |
| `edit` | остаётся как общий признак «может изменять» для совместимости |

Группам, у которых уже был `edit`, автоматически выданы `send_message`,
`shuttle`, `cargo`, `torpedo` и `manage_warehouse` — раньше все они и так
открывались одним этим ключом, так что возможности не изменились.

`manage_webhooks` **намеренно не выдан автоматически**: до разбиения настройка
вебхуков была доступна только суперпользователю, и раздача её нынешним
держателям `edit` была бы расширением прав. Выдайте это право явно тем, кому
оно нужно. Суперпользователь, как и раньше, проходит любую проверку.

## 2. Игровой сервер → NexusData

Аутентификация: заголовок `X-API-Key` со значением `API_KEY` из `.env`
(либо query-параметр `?api_key=`).

### POST `/api/v1/server/dispatch`

Сообщение игрока с радиотерминала.

```json
{
  "steamid": "76561198000000000",
  "player_name": "Ivan",
  "text": "Запрашиваю эвакуацию",
  "server_name": "ASPER1"
}
```

| Поле | Тип | Обязательно | Примечание |
|---|---|---|---|
| `steamid` | string \| null | нет | SteamID64 отправителя |
| `player_name` | string \| null | нет | |
| `text` | string | **да** | до 2000 символов |
| `server_name` | string \| null | нет | `ASPER1` / `ASPER2` |

Ответ: `{"status": "ok", "id": 123}`

Побочные эффекты: сообщение уходит эмбедом в Discord-канал соответствующего
сервера и в исходящий вебхук как событие `dispatch_message`.

### GET `/api/v1/server/dispatch`

Лента сообщений для опроса игровым сервером.

| Параметр | Тип | По умолчанию | Примечание |
|---|---|---|---|
| `limit` | int | 50 | 1…200 |
| `after_id` | int | — | вернуть только `id > after_id` |

Ответ — массив, **отсортированный от старых к новым** (специально: сервер
проигрывает их в правильном порядке):

```json
[{
  "id": 124,
  "steamid": null,
  "player_name": "ND. admin",
  "text": "[Диспетчер] Всем судам — шторм в секторе",
  "sender_type": "dispatcher",
  "server_name": "ASPER1",
  "created_at": "2026-07-28T12:00:00"
}]
```

`sender_type`: `player` — сообщение с радиотерминала, `dispatcher` — от
диспетчера с сайта или из внешней системы.

### POST `/api/v1/server/dispatch/shuttle-departed`

Сервер сообщает, что снабженческий челнок фактически вылетел (срабатывает на
любой реальный вылет — и принудительный, и штатный).

```json
{ "server_name": "ASPER1" }
```

Ответ: `{"status": "ok"}`. Единственный эффект — исходящий вебхук
`shuttle_departed`; в БД ничего не пишется.

### POST `/api/v1/server/round/start`

```json
{
  "server_name": "ASPER1",
  "submarine_name": "Berilia",
  "mission": "Салваж",
  "location": "Outpost Alpha",
  "players": [{"steamid": "7656...", "player_name": "Ivan", "role": null}]
}
```

Ответ: `{"status": "ok", "round_id": 42}`

После сохранения события NexusData автоматически ставит в серверную FIFO
служебный запрос `round_briefing`. Диспетчер ждёт 8 секунд, чтобы успела прийти
первая телеметрия, сканирует сектор и отправляет краткий доклад с возможной
дополнительной работой. Если телеметрия ещё не появилась, выполняется до четырёх
попыток с интервалом 5 секунд. Пустой или выдуманный доклад экипажу не уходит.

Обязательных полей нет — все могут отсутствовать или быть `null`. В записях
`players` по факту нужны только `steamid` и `player_name`; любые другие поля
(`role`, `job` и т.п., в том числе пустые) сохраняются как есть и отдаются
наружу без изменений.

### POST `/api/v1/server/round/end`

```json
{
  "server_name": "ASPER1",
  "mission_completed": true,
  "reached_station": true,
  "players": [{"steamid": "7656...", "player_name": "Ivan"}]
}
```

Ответ: `{"status": "ok", "round_id": 43}`

Событие конца раунда автоматически связывается с последним непарным `start`
того же сервера (`paired_start_id`), поэтому прошедшие раунды достаются одним
запросом. Оба события обновляют статус раунда в Discord.

## 3. Очередь действий (общая для диспетчера и модерации)

Всё, что диспетчер «делает» в игре, попадает сюда. Эндпоинты общие с
модерацией — отдельного канала у диспетчерской нет.

### GET `/api/v1/server/actions`

| Параметр | Тип | Примечание |
|---|---|---|
| `server_name` | string | `ASPER1` / `ASPER2` — вернуть только свои задачи |

Ответ:

```json
[{
  "id": 501,
  "action_type": "cargo_spawn",
  "target_steamid": "system",
  "reason": null,
  "duration_minutes": null,
  "message_text": null,
  "server_name": "ASPER1",
  "queued_at": "2026-07-28T12:00:00",
  "ack_asper1": 0,
  "ack_asper2": 1,
  "payload": {"items": [{"identifier": "oxygentank", "quantity": 5}]}
}]
```

Статус хранится **отдельно по каждому серверу** (`ack_asper1`/`ack_asper2`,
`0` — не выполнено). Задача, адресованная одному серверу, сразу помечается
выполненной для второго — так широковещательные и адресные действия живут в
одной таблице без отдельного флага.

Без `server_name` возвращаются все задачи, у которых хоть один сервер не
отчитался. Указывать `server_name` нужно всегда — иначе сервер заберёт чужие
задачи.

### POST `/api/v1/server/actions/{id}/ack`

```json
{ "success": true, "error_message": null, "server_name": "ASPER1" }
```

`server_name` в теле обязателен для корректного учёта широковещательных задач —
без него нельзя понять, кто именно отчитался.

### Типы действий, которые ставит диспетчерская

| `action_type` | Откуда | `payload` | Что делает сервер |
|---|---|---|---|
| `dispatch` | сообщение диспетчера | — | показывает текст из `message_text` в игре |
| `supply_shuttle_send` | «Отправить челнок» | — | отправляет снабженческий челнок |
| `supply_shuttle_recall` | «Отозвать челнок» | — | отзывает челнок |
| `cargo_spawn` | «Груз в очередь» | `{"items": [{"identifier", "quantity"}]}` | спавнит груз |
| `torpedo_strike` | «Торпедный удар» | `{"x": число, "y": число}` | наносит удар по координатам |

Для `dispatch` текст лежит в `message_text` и всегда начинается с префикса
`[Диспетчер] `, добавляемого сайтом. `target_steamid` у диспетчерских действий
служебный: `broadcast` для сообщений, `system` для остальных.

## 4. Админ-панель

Аутентификация: cookie `admin_token`. Изменяющие запросы дополнительно требуют
CSRF по общим правилам сайта.

### GET `/api/v1/admin/dispatch/messages`

Право: `dispatch:view`.

| Параметр | Тип | По умолчанию |
|---|---|---|
| `after_id` | int | — |
| `server` | string | все |
| `limit` | int | 50 |

Фильтр по серверу **всегда включает сообщения диспетчера без сервера** — они
широковещательные и должны быть видны в обеих лентах.

В ответе, в отличие от игрового `/server/dispatch`, имя отправителя
подменяется административным псевдонимом, если он назначен:

```json
[{
  "id": 124,
  "steamid": "7656...",
  "player_name": "Псевдоним",
  "real_name": "Настоящее имя",
  "text": "...",
  "sender_type": "player",
  "server_name": "ASPER1",
  "created_at": "2026-07-28T12:00:00"
}]
```

`real_name` заполняется только когда псевдоним реально подменил имя, иначе
`null`.

### POST `/api/v1/admin/dispatch/send`

Право: `dispatch:send_message`.

```json
{ "text": "Всем судам — шторм в секторе", "server_name": "ASPER1" }
```

`server_name` необязателен: без него сообщение уходит на оба сервера.
Ответ: `{"status": "ok", "id": 124, "action_id": 501}`

### GET `/api/v1/admin/dispatch/pending?server=ASPER1`

Право: `dispatch:view`. Есть ли неподтверждённое сообщение диспетчера.

```json
{ "pending": true, "action_id": 501 }
```

Необязательный `server` ограничивает проверку каналом `ASPER1` или `ASPER2`.
Без него проверяются **все** задачи типа `dispatch` независимо от того, кто их
поставил, включая пришедшие из внешней системы. При HTTP 409 текст ручной
радиограммы остаётся в поле ввода: оператор может повторить отправку после ACK.

### POST `/api/v1/admin/dispatch/actions/shuttle`

Право: `dispatch:shuttle`.

```json
{ "command": "send", "server_name": "ASPER1" }
```

`command`: `send` или `recall`. `server_name` обязателен.
Ответ: `{"status": "ok", "action_id": 502}`

### POST `/api/v1/admin/dispatch/actions/cargo`

Право: `dispatch:cargo`.

```json
{
  "server_name": "ASPER1",
  "items": [{"identifier": "oxygentank", "quantity": 5}]
}
```

Предметы **списываются с виртуального склада** в той же транзакции, что и
постановка задачи. Если хоть одного предмета не хватает — отклоняется весь
запрос целиком (400 с указанием, чего и сколько не хватает), ничего не
списывается и задача не ставится.

Ответ: `{"status": "ok", "action_id": 503}`

### POST `/api/v1/admin/dispatch/actions/torpedo`

Право: `dispatch:torpedo`.

```json
{ "server_name": "ASPER1", "x": 1500.0, "y": -300.0 }
```

`x` и `y` обязательны и должны быть числами.
Ответ: `{"status": "ok", "action_id": 504}`

Во внешнем клиентском API торпедный удар намеренно **не доступен**.

### GET `/api/v1/admin/round-status`

Право: доступ по сессии. Сводка по обоим серверам для страницы «Статус раунда»:

```json
{
  "ASPER1": {
    "active": true,
    "location": "Outpost Alpha",
    "submarine_name": "Berilia",
    "mission": "Салваж",
    "started_at": "2026-07-28T11:00:00",
    "player_count": 14,
    "submarine_health": 87.5,
    "shuttle_arrival_at": "2026-07-28T12:05:00Z"
  },
  "ASPER2": { "...": "..." }
}
```

Состояние раунда вычисляется из событий `start`/`end`: раунд активен, если
последний `start` новее последнего `end`.

### Настройки вебхуков — право `dispatch:manage_webhooks`

**GET** `/api/v1/admin/dispatch/webhook-config` →
`{"ASPER1": "https://...", "ASPER2": null}`

**PATCH** `/api/v1/admin/dispatch/webhook-config` — передавать можно один ключ
или оба, отсутствующие не трогаются; `null` или пустая строка очищает адрес:

```json
{ "ASPER1": "https://example.com/hook", "ASPER2": null }
```

URL обязан начинаться с `http://` или `https://`, иначе 400. Ответ — состояние
после изменения.

## 5. Виртуальный склад

Склад — общий на оба сервера, не разделён по серверам. Он ограничивает выдачу
грузов: `cargo_spawn` списывает из него остатки.

### Админ-панель

| Метод | Путь | Право | Назначение |
|---|---|---|---|
| GET | `/api/v1/admin/warehouse` | `view` | остатки + флаг `can_edit` |
| POST | `/api/v1/admin/warehouse/items` | `manage_warehouse` | добавить позицию либо задать точное количество существующей (upsert по `identifier`) |
| PATCH | `/api/v1/admin/warehouse/items/{identifier}` | `manage_warehouse` | изменить количество |
| DELETE | `/api/v1/admin/warehouse/items/{identifier}` | `manage_warehouse` | удалить позицию |

POST принимает `{"identifier": "oxygentank", "quantity": 100}` — количество
абсолютное, целое ≥ 0.

PATCH принимает **одно из двух**:

* `{"quantity": 100}` — задать точное количество;
* `{"delta": -5}` — изменить относительно текущего, результат не опускается
  ниже нуля.

Если не передано ни то, ни другое — 400.

### GET `/api/v1/client/warehouse`

Аутентификация: `X-API-Key: <CLIENT_API_KEY>`. Только чтение, всегда живые
данные без кеша:

```json
{ "items": [{"identifier": "oxygentank", "quantity": 42}] }
```

`identifier` — идентификатор предмета Barotrauma. Названия и иконки для
интерфейса берутся из `static/item_catalog.json`.

## 6. Внешний клиентский API

Аутентификация: `X-API-Key: <CLIENT_API_KEY>` (либо `?api_key=`). Админ-сессия
не нужна. Повторяет три действия админ-панели, кроме торпедного удара.

Задачи, поставленные отсюда, ничем не отличаются от поставленных админом,
кроме пустого автора (`queued_by_admin_id = null`).

### GET `/api/v1/client/world/state`

Актуальное состояние мира. Поддерживает два необязательных query-параметра:

| Параметр | Назначение |
|---|---|
| `round_id` | вернуть конкретный раунд, включая уже неактивный; неизвестный ID даёт 404 |
| `server_name` | ограничить результат сервером (`ASPER1` или `ASPER2`) |

Без `round_id` возвращаются только активные раунды. Ответ всегда имеет форму
`{"rounds": [...]}` и передаётся с `Content-Encoding: gzip`.

### POST `/api/v1/client/dispatch/cargo`

```json
{ "server_name": "ASPER1", "items": [{"identifier": "oxygentank", "quantity": 5}] }
```

Та же проверка склада, что и в панели: не хватило — 400, ничего не списано.

### POST `/api/v1/client/dispatch/shuttle`

```json
{ "server_name": "ASPER1", "command": "send" }
```

### POST `/api/v1/client/dispatch/message`

```json
{
  "server_name": "ASPER1",
  "text": "Сообщение от внешней системы",
  "sender_name": "Название системы"
}
```

`sender_name` необязателен, по умолчанию «Внешняя система». Он попадает в
историю как имя отправителя; сам текст в игре всё равно получит префикс
`[Диспетчер] `.

Ответ: `{"status": "ok", "id": 125, "action_id": 505}`

## 7. Исходящие вебхуки

Настраиваются отдельно для каждого сервера (суперпользователем). Если адрес не
задан — событий просто нет.

Доставка **best-effort**: отправляется в фоновом потоке, не блокирует запрос,
ошибки не влияют на основную операцию и **повторов нет**. Вебхук — способ
уведомить, а не гарантированная очередь; источник истины всегда БД сайта.

Общий формат тела (POST, JSON):

```json
{
  "event": "dispatch_message",
  "server_name": "ASPER1",
  "timestamp": "2026-07-28T12:00:00.000000Z",
  "...": "поля, специфичные для события"
}
```

| `event` | Когда | Дополнительные поля |
|---|---|---|
| `dispatch_message` | игрок написал с радиотерминала | `steamid`, `player_name`, `text` |
| `shuttle_send_requested` | запрошена отправка челнока | — |
| `shuttle_departed` | челнок фактически вылетел | — |

Отзыв челнока события не порождает. `timestamp` — UTC.

## 8. Интеграция с Discord

Сообщения диспетчерской дублируются эмбедом в канал соответствующего сервера
(каналы настраиваются на странице Discord-бота, ключи
`dispatch_channel_asper1_id` / `dispatch_channel_asper2_id`).

* Сообщение диспетчера без указания сервера уходит **в оба канала**.
* Подпись сообщения игрока — текущая локация из активного раунда, а если раунд
  не идёт, «Неизвестный сектор».

Работа с Discord требует корректного `GUILD_ID` в `.env` — без него бот не
найдёт сервер и отправка эмбедов молча не сработает.

## 9. Коды ответов

| Код | Значение |
|---|---|
| 200 | успех |
| 400 | некорректное тело: нет сервера, пустой текст, битые координаты, нехватка на складе |
| 401 | неверный или отсутствующий ключ / нет сессии |
| 403 | нет соответствующего права страницы `dispatch` (см. раздел 1) |
| 404 | задача для ACK не найдена |
| 409 | радиоканал диспетчера занят предыдущей неподтверждённой передачей |

Ошибки приходят в стандартном виде FastAPI: `{"detail": "текст"}`.

## 10. Пример: внешняя система

```bash
KEY="ваш CLIENT_API_KEY"
BASE="https://nd.rp-asper.ru"

# остатки склада
curl -s -H "X-API-Key: $KEY" "$BASE/api/v1/client/warehouse"

# груз (спишется со склада)
curl -s -X POST -H "X-API-Key: $KEY" -H "Content-Type: application/json" \
  -d '{"server_name":"ASPER1","items":[{"identifier":"oxygentank","quantity":5}]}' \
  "$BASE/api/v1/client/dispatch/cargo"

# челнок
curl -s -X POST -H "X-API-Key: $KEY" -H "Content-Type: application/json" \
  -d '{"server_name":"ASPER1","command":"send"}' \
  "$BASE/api/v1/client/dispatch/shuttle"

# сообщение диспетчера
curl -s -X POST -H "X-API-Key: $KEY" -H "Content-Type: application/json" \
  -d '{"server_name":"ASPER1","text":"Шторм в секторе","sender_name":"Метеослужба"}' \
  "$BASE/api/v1/client/dispatch/message"
```

## 11. Интеграция с AsperAIDispatcher

NexusData может напрямую пересылать все сообщения игроков в AI-диспетчер. Сам
AI локально проверяет наличие обращения «Диспетчер» с учётом опечаток. Обычные
сообщения получают статус `ignored` и не создают ответного действия.

Переменные NexusData:

```env
AI_DISPATCHER_URL=http://127.0.0.1:8000/api/v1/dispatcher/messages
AI_DISPATCHER_API_KEY=тот-же-ключ-что-DISPATCHER_API_KEY-в-AI
AI_DISPATCHER_TIMEOUT_SECONDS=60
```

Поток данных:

1. игровой сервер отправляет сообщение в `POST /api/v1/server/dispatch`;
2. NexusData сохраняет его и в фоновом потоке вызывает AsperAIDispatcher;
3. AI фильтрует позывной и при необходимости читает состояние мира или склад
   через `CLIENT_API_KEY`;
4. ответ AI попадает в отдельную FIFO-очередь своего сервера. Очередь ограничена
   100 запросами на процесс, чтобы сбой игрового сервера не расходовал память
   без ограничения. Перед
   каждой радиограммой NexusData выдерживает от 4 до 12 секунд пропорционально
   её длине, сохраняет её как `ИИ-диспетчер` и ставит одно действие `dispatch` в
   `server_actions`. Следующая часть не создаётся, пока игровой сервер не подтвердит
   предыдущую через успешный ACK, поэтому один опрос `/server/actions` не может
   забрать весь ответ сразу;
5. игровой сервер забирает действие через `/api/v1/server/actions` и
   подтверждает выполнение через ACK.

Событие начала выхода проходит через ту же FIFO и тот же механизм ACK, поэтому
первичный доклад не накладывается на ответы экипажу. Для него NexusData передаёт
`message_type: "round_briefing"` и вводную из `/round/start`; обычные сообщения
используют значение `terminal_message` по умолчанию.

Интеграция не блокирует приём сообщения игрового сервера: недоступность AI
пишется в лог NexusData, но исходный `POST /server/dispatch` остаётся успешным.
Задержка и ожидание ACK тоже выполняются только в фоновом потоке. Ожидание
свободного канала и ACK ограничено 90 секундами; тайм-аут или неуспешный ACK
останавливает оставшиеся части ответа. Неподтверждённое действие при тайм-ауте
атомарно помечается неуспешным, поэтому оно не блокирует канал и не появляется
после позднего переподключения сервера. Запросы ASPER1 и ASPER2 обрабатываются
параллельно. В одном процессе порядок одного сервера — FIFO; при нескольких
Uvicorn-процессах файловая блокировка гарантирует отсутствие наложения, но не
обещает абсолютный порядок одновременно принятых разными процессами запросов.
Ручная или внешняя радиограмма может пройти во время задержки AI: передача AI
дождётся её ACK. HTTP 409 возвращается только если в `server_actions` уже есть
неподтверждённая радиограмма для того же сервера.
Задание AI живёт не более 180 секунд. Перед вызовом модели, перед каждой
задержкой и непосредственно перед записью действия NexusData сверяет раунд;
ответ из завершившегося раунда без отправки удаляется из очереди.
Для маршрутизации ответа поле `server_name` должно быть `ASPER1` или `ASPER2`.
`round_id` привязан к событиям `round/start` и `round/end`, поэтому пауза или
возобновление телеметрии не меняет беседу посреди раунда. Если сервер не
отправляет события жизненного цикла, резервным стабильным якорем служит
последний известный `WorldRound`. AI ведёт одну ограниченную историю разговора
на сервер и раунд.

Barotrauma принимает не более 200 символов одного радиосообщения. NexusData
добавляет префикс `[Диспетчер] `, поэтому каждый элемент `replies` от AI
ограничен 188 символами. Один ответ занимает не более трёх передач; если сводка
длиннее, третья передача просит уточнить нужный раздел. Поле `reply`
поддерживается как совместимый одиночный ответ; NexusData дополнительно делит
слишком длинные старые ответы по границам предложений, знакам препинания и
словам и применяет тот же предел.
