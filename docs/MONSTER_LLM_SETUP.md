# LLM-ассистент MonsterSpawnController

Сайт обращается к модели ТОЛЬКО через общий AI-агрегатор
(`AI_DOSSIER_URL` + `AI_DOSSIER_API_KEY`, TLS — `AI_DOSSIER_TLS_CA_FILE`,
код — `services_ai_client.py`). Ассистент монстров — клиент долговременной
очереди `services_llm_gateway.py` (`monster_llm`): общий воркер выполняет
его генерации последовательно с досье и другими клиентами на
Qwen/KoboldCpp хосте. Отдельного endpoint/ключа у монстров нет.
Ассистент анализирует состояние спавн-контроллера, даёт текстовые
рекомендации и сводку эффективности экипажа, корректирует параметры
сложности и спавнит волны по обстановке или команде оператора.
Интеграция полностью серверная (сайт), плагин ничего не знает о модели — он получает
уже провалидированные изменения через штатный канал ревизий.

## 1. Подключение через AI-агрегатор

Транспортные настройки берутся из AI-агрегатора (те же, что у досье):

```env
AI_DOSSIER_URL=https://213.108.170.48:8000/v1/chat/completions
AI_DOSSIER_API_KEY=...
AI_DOSSIER_TLS_CA_FILE=config/koboldcpp-ca.pem
```

Ассистент шлёт туда обычный OpenAI-совместимый `POST /chat/completions`
(`system/user/assistant`, текстовый ответ с JSON-объектом по схеме из
`services_llm_monster.py`, `SYSTEM_PROMPT`). Пустые `AI_DOSSIER_URL` или
`AI_DOSSIER_API_KEY` отключают функцию с ошибкой
«AI-агрегатор не настроен».

Старые ключи `MONSTER_LLM_BASE_URL` / `MONSTER_LLM_API_KEY` больше не
используются и удалены: второй путь в обход очереди не заводится
намеренно (см. `services_llm_gateway.py`).

## 2. Настройки сайта (`.env`)

```env
# Транспорт — общий агрегатор (те же ключи, что у досье, см. раздел 1).
MONSTER_LLM_MODEL=qwen3-4b-instruct
MONSTER_LLM_TIMEOUT_SECONDS=90
MONSTER_LLM_TEMPERATURE=0.15
MONSTER_LLM_TOP_P=0.8
MONSTER_LLM_AUTO_INTERVAL_MINUTES=0   # 0 = только ручные запуски
```

После установки значений перезапустите `api_server.py`.
Включение ассистента и автопилота — в UI: «Управление монстрами» → вкладка **LLM-ассистент**.

## 3. Настройки модели против галлюцинаций

Модель работает в режиме «верни строго JSON по схеме», поэтому:

| Параметр | Значение | Причина |
|---|---|---|
| temperature | **0.15** (аварийный повтор — 0.0) | детерминированные ответы, никакого «творчества» |
| top_p | **0.8** | отсекает хвост маловероятных токенов |
| max_tokens | 2048 | JSON помещается, обрыв маловероятен |
| thinking mode | отключён (`chat_template_kwargs.enable_thinking=false`) | рассуждения идут вне JSON и ломают парсинг |
| response schema | жёсткая, проверяется кодом | невалидный JSON → 1 повтор → отбрасывание с записью ошибки |
| analyzer text | `crew_summary` + `recommendations` всегда | текстовая сводка и советы оператору, в конфиг не пишутся |

Даже если модель «галлюцинирует», защита на стороне сайта не даст навредить:

1. **Whitelist параметров.** Модель может менять только зарегистрированные ключи
   (`max_short_term_difficulty`, `target_difficulty_per_minute`, `intensity_threshold`,
   `vanilla_events.amount_multiplier` и т.д. — полный список в `services_llm_monster.py`,
   константы `EDITABLE_*` и `VANILLA_FLOAT_KEYS`). Остальные ключи отбрасываются.
2. **Жёсткие границы значений.** Каждая операция приводится к диапазону
   `[hard_min, hard_max]` независимо от того, что вернула модель.
3. **Ограничение шага.** За один цикл параметр может сдвинуться не больше чем на
   `max_step` (например, сложность — не более ±3.0, порог интенсивности — не более ±0.15).
4. **Виды монстров только из известных.** Спавн разрешён только видов из
   `known_species` (память угроз/мобильности + текущие волны конфига). Выдуманный вид
   отбрасывается до записи плана.
5. **Лимиты спавна.** Не более 6 существ на запрос, не более 6 запросов за цикл,
   hp_multiplier в [0.5, 2.0].
6. **Полный аудит.** Каждый запуск сохраняет `last_result` (ситуация, сводка экипажа,
   рекомендации, применённое, отклонённое с причинами, уверенность) — видно в UI.
7. **Дефолт без автопилота.** Пока оператор не включил `auto_apply` и интервал,
   модель работает в режиме `analyze` — текстовый анализатор: ситуация + сводка
   эффективности экипажа + рекомендации, без изменения конфига.

## 4. Как это работает

1. Сайт собирает состояние контроллера: конфиг, память (эффективность волн/кораблей,
   потери экипажа, урон лодке), телеметрию (активные волны, темп, изученные волны,
   угрозы видов) — из таблицы `monster_spawn_controls`.
2. Формируется промпт: системный (роль + схема JSON + правила) и пользовательский
   (состояние + список разрешённых ключей с границами + известные виды + команда оператора).
3. Модель возвращает JSON: `situation`, `crew_summary` (сводка эффективности экипажа
   текстом), `recommendations` (до 5 текстовых советов оператору), `config_changes`,
   `spawn_requests`, `confidence`. Текстовый блок показывается в UI всегда, даже в
   режиме `analyze`.
4. Ответ валидируется и клампится; изменения применяются через `desired_revision += 1`
   — тот же канал, что и ручное редактирование в UI. Плагин подхватит их в течение ~10 секунд.
5. Спавн-запросы превращаются в планы (`source: "llm"`) с координатой относительно
   подлодки (`position_hint`: ahead/around/below). План виден на карте в «Визуальном управлении».

## 5. Промпты

Промпты зашиты в `services_llm_monster.py` (`SYSTEM_PROMPT`, `_build_user_prompt`) —
именно так исключается расхождение между валидатором и инструкцией модели: список
разрешённых ключей и границы попадают в промпт из того же реестра, который использует валидатор.

Ключевые правила, переданные модели:
- только JSON без markdown;
- crew_summary и recommendations — всегда, текстом по-русски для оператора;
- менять параметры плавно, при малом объёме данных — не менять ничего;
- спавн — только при явной необходимости или прямой команде оператора;
- запрещено выдумывать данные, которых нет в состоянии.

## 6. Ручные команды оператора (асинхронно)

POST `/api/v1/admin/monster-spawn/llm/run?server=ASPER1` только СТАВИТ цикл
в очередь и сразу возвращает **HTTP 202** `{"status": "queued", "run": {...}}`
— HTTP-запрос никогда не ждёт генерацию: цикл в общей очереди AI-центра
плюс до двух таймаутов модели легко переживает 180-секундный read-таймаут
прокси (раньше это выглядело как зависшая кнопка «Модель думает…» и HTTP 504).
Если цикл уже стоит в очереди или выполняется — **HTTP 409**. Исполняет
воркер `monster_llm_runs` (раз в 10 с), результат появляется в `llm/runs`
(`result`, `pending_run`/`active_run`) — UI опрашивает его раз в 10 с.

```json
{"mode": "spawn", "instruction": "Заспавни 2 мадрэпторов впереди по курсу, экипаж скучает"}
```

- `mode: "analyze"` — анализатор: ситуация + сводка эффективности экипажа + рекомендации текстом (конфиг не трогает, но результат сохраняется и виден в UI);
- `mode: "apply"` — применить провалидированные изменения конфига;
- `mode: "spawn"` — то же + заспавнить волны по решению модели/команде.

## 7. API сводка

| Метод | Путь | Описание |
|---|---|---|
| GET | `/api/v1/admin/monster-spawn/llm/runtime?server=` | статус ассистента + deployment |
| PUT | `/api/v1/admin/monster-spawn/llm/runtime?server=` | включить/выключить, интервал автопилота |
| POST | `/api/v1/admin/monster-spawn/llm/run?server=` | поставить LLM-цикл в очередь (202; 409 если занято) |
| POST | `/api/v1/admin/monster-spawn/llm/apply-proposal?server=` | применить проверенные предложения к неизменённому конфигу |
| GET | `/api/v1/admin/monster-spawn/reports?server=` | все сохранённые раунды со статусом и заключением LLM |

Права: просмотр — `monster_spawn:view`, запуск/настройка — `monster_spawn:edit`.
