# WorldStateStreamer — инструкция для API-сервера

Этот документ описывает, что именно шлёт плагин `WorldStateStreamer.cs` (файл в
корне репозитория) на внешний API, и что нужно реализовать на стороне API,
чтобы это принимать. Формат зафиксирован кодом плагина — здесь просто его
контракт, ничего не нужно "придумывать" отдельно.

Плагин пока выключен (`Enabled: false` в конфиге) — включить можно только
когда API готов отвечать 2xx на оба эндпоинта ниже.

---

## 1. Общая схема

Два эндпоинта, оба `POST`, оба `application/json`:

| Эндпоинт | Когда шлётся | Что несёт |
|---|---|---|
| `POST {ApiBaseUrl}/world/init` | Один раз в начале раунда (`roundStart`) | Статическая геометрия: отсеки, стены, двери, контур уровня, список подлодок |
| `POST {ApiBaseUrl}/world/snapshot` | Каждые `SnapshotIntervalSeconds` (по умолчанию **3 секунды**) пока раунд идёт | Динамика: персонажи, предметы, отсеки (вода/кислород), двери (открытость), реакторы, позиции подлодок |

`ApiBaseUrl` задаётся в `LocalMods/MorePlugins/world_state_config.json`
(создаётся автоматически при первом запуске плагина), например
`https://your-api/api/v1/` — тогда реальные адреса будут
`https://your-api/api/v1/world/init` и `.../world/snapshot`.

**Геометрия не дублируется в каждом снапшоте** — это специально: стены/отсеки/двери
не двигаются относительно своей подлодки, а привязку геометрии к позиции
подлодки в конкретный момент даёт `subs[]` внутри `world/snapshot` (см. §4).

---

## 2. Аутентификация и заголовки

- `X-API-Key: <ApiKey>` — только если `ApiKey` непустой в конфиге плагина. **Другие
  способы (Bearer-токен, query-параметр) плагин не отправляет** — только этот заголовок.
- `Content-Type: application/json`
- `Content-Encoding: gzip` — **только если** в конфиге включено `CompressPayload: true`
  (по умолчанию выключено). Если включаете эту опцию на своей стороне — API
  обязан **уметь разжимать gzip-тело запроса**, иначе получите мусор вместо JSON.
  Пока не реализуете декомпрессию — не трогайте эту настройку в конфиге плагина.
- `User-Agent: BarotraumaWorldStateStreamer/1.0`

Формат ключа/заголовка полностью на вашей стороне — просто ожидайте `X-API-Key`
в каждом запросе на оба эндпоинта, если решите требовать авторизацию.

---

## 3. Что должен вернуть API

Плагин **не парсит и не использует тело ответа вообще**. Единственное, что имеет
значение — HTTP статус:

- **2xx** — считается успехом. Можно возвращать `{}`, `"ok"`, пустое тело — что угодно.
- **не 2xx** (включая 4xx/5xx) — считается ошибкой: попадёт в лог сервера (не чаще
  раза в 30 секунд, чтобы не спамить, пока API недоступен), тело ответа (до 200
  символов) попадёт в текст ошибки — **можно возвращать текст причины в теле при
  ошибке, он будет виден в логе игрового сервера**, это полезно для отладки.

**Плагин НЕ делает повторных попыток** при неудаче — ни ретраев, ни очереди.
Если `world/snapshot` не долетел — просто через 3 секунды прилетит следующий,
более свежий. Из этого следует главное требование к API:

> **Каждый снапшот — это независимое "текущее состояние", а не событие в
> журнале.** Обрабатывайте его как upsert (перезаписать последнее известное
> состояние раунда), а не как append-only лог, требующий полноты. Если API
> временно недоступен 10 секунд — 3 снапшота потеряются безвозвратно, это
> нормально и ожидаемо, гнаться за ними не нужно.

Рекомендация: отвечайте 2xx максимально быстро (просто сохранили тело в очередь/
таблицу и всё), а тяжёлую обработку (агрегация, индексация, вебсокет-рассылка
на фронтенд и т.п.) делайте асинхронно после ответа — плагин ждёт ответ до
`RequestTimeoutSeconds` (по умолчанию 8с), и хотя долгий ответ не ломает
поток данных (следующий тик всё равно пойдёт независимо благодаря
troppy-защите ниже), лучше не тратить это время впустую.

## 4. Конкурентность на стороне сервера-источника (важно для интерпретации данных)

- В любой момент времени с одного игрового сервера может лететь **не больше
  одного** `world/snapshot`-запроса одновременно — плагин физически не пришлёт
  следующий, пока не получит ответ (успех/ошибку/таймаут) на предыдущий.
  Значит, для одного `shard`/сервера снапшоты гарантированно приходят
  **последовательно и в порядке `seq`** (см. ниже) — беспокоиться об out-of-order
  доставке **в рамках одного сервера** не нужно.
- `world/init` может прийти почти одновременно с самым первым `world/snapshot`
  того же раунда (оба независимые HTTP-запросы) — обрабатывайте их как два
  отдельных эндпоинта без взаимной блокировки; `world/snapshot` может даже
  прийти до того, как обработка `world/init` завершится на вашей стороне —
  это нормально, просто не полагайтесь на строгий порядок между ними.
- Если у вас **несколько игровых серверов** шлют данные на один API — все поля
  ниже (кроме `round_id`) не содержат идентификатора сервера. **Добавьте
  собственную привязку по API-ключу или IP на своей стороне**, если нужно
  различать несколько источников — плагин сейчас не передаёт "shard_id"/
  "server_name" в `world/snapshot` (только в `world/init`, см. `server_name`).

## 5. `POST /world/init` — статическая геометрия раунда

Присылается **один раз** при старте раунда (и повторно, если плагин
хот-релоаднулся посреди уже идущего раунда). Новый `round_id` = новый раунд —
не пытайтесь "дополнять" геометрию предыдущего раунда данными нового.

```json
{
  "round_id": "3f9a1c2b4e5d4a7c9b0e1f2a3c4d5e6f",
  "server_name": "ASPER1",
  "level_seed": "abc123",
  "level_name": "Europan Ridge",
  "level_type": "LocationConnection",
  "level_w": 100000,
  "level_h": 50000,
  "sub_name": "Orca",
  "submarines": [
    { "id": 1, "name": "Orca" },
    { "id": 2, "name": "Rescue Shuttle" }
  ],
  "hulls": [
    { "id": 12, "sub": 1, "r": [-500, -300, 200, 150] }
  ],
  "walls": [
    { "sub": 1, "r": [-500, -300, 200, 20], "h": true, "p": false }
  ],
  "doors": [
    { "id": 87, "sub": 1, "r": [-300, -300, 32, 100], "h": false }
  ],
  "outline_w": 100000,
  "outline_h": 50000,
  "outline": [
    [[1000, 2000], [1050, 2000], [1050, 2100], [1000, 2100]]
  ],
  "sent_at": 1753000000000
}
```

### Поля

| Поле | Тип | Описание |
|---|---|---|
| `round_id` | string | Уникальный ID раунда (guid без дефисов). Ключ, по которому всё связывается со снапшотами того же раунда. |
| `server_name` | string | `GameMain.Server.ServerName`. |
| `level_seed` | string | Сид уровня. |
| `level_name` | string | Биом/название уровня (для отображения). |
| `level_type` | string | Enum-тип уровня как строка (`LocationConnection`, `Outpost` и т.д.). |
| `level_w`, `level_h` | int | Размер уровня в игровых единицах. |
| `sub_name` | string | Имя основной подлодки (`Submarine.MainSub`). |
| `submarines[]` | array | Все загруженные подлодки: `id` (стабилен в рамках раунда), `name`. |
| `hulls[]` | array | Отсеки. `r` = `[x, y, width, height]`, **координаты ОТНОСИТЕЛЬНО позиции подлодки `sub`** в момент отправки init (sub-local), не мировые! |
| `walls[]` | array | Стены. `r` — тот же sub-local формат. `h` = горизонтальная, `p` = платформа (не блокирует). |
| `doors[]` | array | Геометрия дверей. `id` = ID предмета-двери (используется для связи с `doors[]` в снапшоте). `r` — sub-local. |
| `outline_w`, `outline_h` | int | Размер уровня (дублирует `level_w`/`level_h`, для удобства). |
| `outline[]` | array of polygons | Контур стен/пещер уровня. Каждый полигон — массив точек `[x, y]` **в МИРОВЫХ координатах** (это не подлодка, это статичный ландшафт уровня, sub-relative тут неприменимо). Может быть до `MaxWorldOutlinePolygons` (по умолчанию 20000) полигонов — рассчитывайте на потенциально многомегабайтный payload. |
| `sent_at` | long | Unix-время отправки в миллисекундах (UTC). |

### ⚠️ Как получить мировые координаты геометрии

`hulls[]`/`walls[]`/`doors[]` заданы **относительно подлодки** (`sub` = id
подлодки), а не в мировых координатах. Чтобы получить мировую позицию
прямоугольника в конкретный момент времени:

```
world_x = hull.r[0] + sub_position.x
world_y = hull.r[1] + sub_position.y
```

где `sub_position` — текущая позиция подлодки с этим `id` из **последнего
полученного** `world/snapshot.subs[]` (см. §6). Подлодка может двигаться
(например, в открытом море), поэтому мировые координаты геометрии нужно
пересчитывать на каждый снапшот, даже если сама геометрия (`hulls`/`walls`/
`doors`) присылается один раз за раунд и не меняется.

## 6. `POST /world/snapshot` — динамическое состояние

Присылается каждые `SnapshotIntervalSeconds` (по умолчанию 3с), пока раунд
идёт. Любое поле-массив может быть `null`/отсутствовать, если соответствующих
сущностей в мире нет (кроме `items`, который явно `null`, когда в конфиге
плагина `IncludeItems: false`).

```json
{
  "round_id": "3f9a1c2b4e5d4a7c9b0e1f2a3c4d5e6f",
  "seq": 42,
  "t": 126.7,
  "sent_at": 1753000126700,
  "subs": [
    { "id": 1, "x": 15230, "y": -8420 }
  ],
  "hulls": [
    { "id": 12, "water": 0.0, "oxygen": 98.4, "fire": 0 }
  ],
  "doors": [
    { "id": 87, "open": 100.0 }
  ],
  "reactors": [
    {
      "id": 55, "sub": 1, "power_on": true,
      "fission": 42.1, "turbine": 45.0, "load": 3200.0,
      "max_output": 10000.0, "temp": 55.2, "fuel": 78.0,
      "critical": false, "melted": false
    }
  ],
  "characters": [
    {
      "id": 3, "name": "Иван Петров", "species": "human", "human": true,
      "team": "Team1", "job": "captain", "steamid": "76561198000000000",
      "x": 15300, "y": -8390, "hp": 100.0, "oxygen": 100.0,
      "dead": false, "water": false, "ragdoll": false, "dir": 1, "hull": 12
    }
  ],
  "items": [
    {
      "id": 901, "item": "revolver", "x": 15290, "y": -8395,
      "cond": 87.5, "owner_t": "character", "owner_id": 3
    }
  ]
}
```

### Поля верхнего уровня

| Поле | Тип | Описание |
|---|---|---|
| `round_id` | string | Совпадает с `round_id` из `world/init` этого раунда — по этому полю связывайте снапшот с геометрией. |
| `seq` | long | Монотонно растущий номер снапшота **в рамках раунда**, начиная с 1. **Не гарантируется непрерывность** — если сборка/сериализация одного тика заняла дольше `SnapshotIntervalSeconds`, следующий тик пропускается целиком (см. §4/§7), поэтому в последовательности `seq` возможны дыры. Используйте для сортировки/детекта "это старее уже полученного — игнорировать", а не для подсчёта "сколько всего должно было прийти". |
| `t` | float | Секунды с начала раунда (`GameSession.RoundDuration`). |
| `sent_at` | long | Unix-время отправки, миллисекунды UTC. |
| `subs[]` | array | Текущие мировые позиции подлодок: `id`, `x`, `y`. Используйте для пересчёта sub-local геометрии из `world/init` в мировые координаты (см. §5). |
| `hulls[]` | array | `id`, `water` (0–100, % заполнения водой), `oxygen` (0–100, % кислорода), `fire` (0–255, количество очагов огня в отсеке). |
| `doors[]` | array | `id` = ID предмета-двери (сопоставляйте с `doors[].id` из init), `open` (0–100, % открытости). |
| `reactors[]` | array | По одному объекту на каждый предмет с компонентом Reactor во всём мире. `id` = ID предмета, `sub` = ID подлодки-владельца. `fission`/`turbine`/`temp` — проценты 0–100. `load`/`max_output`/`fuel` — абсолютные величины движка (кВт/условные единицы топлива). `critical` — температура в критической зоне. `melted` — уже произошёл meltdown в этом раунде. |
| `characters[]` | array | См. ниже. |
| `items[]` | array\|null | См. ниже. `null`, если у плагина выключен сбор предметов (`IncludeItems: false` в конфиге) — в этом случае просто не обновляйте предметы на этом тике, не считайте это "все предметы исчезли". |

### `characters[]`

| Поле | Тип | Описание |
|---|---|---|
| `id` | ushort | ID персонажа в рамках раунда (переиспользуется движком между раундами и даже внутри раунда при деспавне/спавне новых существ — **не используйте как постоянный ключ игрока между раундами**, для этого есть `steamid`). |
| `name` | string | Отображаемое имя. |
| `species` | string | Идентификатор вида (`human`, `moloch`, `hammerhead`, ...). |
| `human` | bool | Игрок/гуманоид-NPC (true) или существо (false). |
| `team` | string | `"Team1"` \| `"Team2"` \| `"None"` \| `"FriendlyNPC"`. |
| `job` | string\|null | Идентификатор профессии (`captain`, `mechanic`, ...), `null` у существ и у гуманоидов без профессии. |
| `steamid` | string\|null | SteamID64 игрока-владельца, если это управляемый игроком персонаж и сервер смог получить AccountId; `null` для ботов/существ/NPC. |
| `x`, `y` | int | Мировые координаты (не sub-local). |
| `hp` | float | Здоровье, 0–**200** (может быть выше 100 при бонусах — не клэмпайте на своей стороне). |
| `oxygen` | float | Кислород персонажа, 0–100. |
| `dead` | bool | Мёртв. |
| `water` | bool | В воде. |
| `ragdoll` | bool | В рэгдолле (оглушён/сбит с ног). |
| `dir` | int | `-1` — смотрит влево, `1` — вправо. |
| `hull` | ushort\|null | ID текущего отсека (`hulls[].id` из init), `null` — персонаж вне какого-либо отсека (открытая вода/за бортом). |

### `items[]`

Полный список предметов в мире (ограничен `MaxItems`, по умолчанию 20000 —
если предметов больше, лишние **отбрасываются без предупреждения на этом
тике**, порядок отбрасывания не гарантирован между тиками).

| Поле | Тип | Описание |
|---|---|---|
| `id` | ushort | ID предмета. |
| `item` | string\|null | Идентификатор префаба (`revolver`, `oxygenite`, ...). |
| `x`, `y` | int | Мировые координаты. |
| `cond` | float | Состояние предмета, 0–100 (% от максимального). |
| `owner_t` | string | `"character"` — в инвентаре/экипировке персонажа (см. `owner_id`); `"item"` — внутри другого предмета-контейнера (сундук, рюкзак, оружие с патроном и т.п.); `"hull"` — лежит на полу в отсеке; `"world"` — вне отсеков (открытая вода/затоплено за бортом). |
| `owner_id` | ushort\|null | ID владельца согласно `owner_t` (ID персонажа / ID предмета-контейнера / ID отсека). `null`, если `owner_t == "world"`. |

**Важно:** экипировка/инвентарь персонажей **не дублируется** отдельным
полем внутри `characters[]` — держимые/надетые предметы уже есть в общем
`items[]` с `owner_t: "character"` и `owner_id` = ID персонажа. Если нужно
"что несёт игрок X" — фильтруйте `items[]` по `owner_id == X.id`. Контейнеры
могут быть вложенными: предмет внутри рюкзака в руках у игрока будет иметь
`owner_t: "item"`, `owner_id` = ID рюкзака, а сам рюкзак — `owner_t:
"character"`, `owner_id` = ID игрока; стройте иерархию рекурсивно, если нужно.

## 7. Рекомендации по реализации API

1. **Отвечайте быстро и всегда 2xx**, если тело успешно распарсилось и
   сохранилось — не делайте синхронную тяжёлую обработку в хендлере.
2. **Не требуйте идемпотентности/ретраев** — плагин их не делает и не
   планирует; API должен быть готов к тому, что отдельные снапшоты просто не
   долетят, без каких-либо признаков этого на стороне игрового сервера.
3. **Ключ хранения — `round_id`**, а не время: `world/init` создаёт
   запись/раунд, `world/snapshot` с тем же `round_id` — обновляет "последнее
   известное состояние" этого раунда (upsert, не insert-every-row), если вам
   не нужна полная история каждого тика.
4. Если нужна **история по времени** (а не только последнее состояние) —
   пишите `world/snapshot` как append-only с индексом `(round_id, seq)`, учитывая
   пункт про дыры в `seq` из §6.
5. **`items[]` может быть большим** (до 20000 объектов = за раунд с активными
   игроками легко несколько МБ JSON каждые 3 секунды) — используйте потоковый
   JSON-парсер на входе, а не загрузку всего тела в память как строку, если
   ваш веб-фреймворк по умолчанию так делает.
6. Если решите включить `Content-Encoding: gzip` на стороне плагина —
   убедитесь, что ваш HTTP-сервер/фреймворк **декомпрессирует тело запроса
   автоматически** (многие веб-фреймворки декомпрессируют только ОТВЕТЫ по
   умолчанию, а не ВХОДЯЩИЕ запросы) — иначе получите бинарный мусор вместо JSON.
7. Отдельного эндпоинта "на конец раунда" плагин не шлёт — конец раунда
   определяйте по отсутствию новых `world/snapshot` с данным `round_id` дольше
   `SnapshotIntervalSeconds * N` (например, 3–5 пропущенных интервалов) —
   таймаут на своей стороне, а не явный сигнал.
